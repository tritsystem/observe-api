How it works

An embedding model, a real vector index, and a rerank step that admits its own limits.

Every repo is chunked at function boundaries (not fixed-size windows), embedded with stock all-MiniLM-L6-v2 — deliberately stock: a fine-tuned variant was built and measured worse on real retrieval, twice, at two different corpus sizes (see the benchmarks below) — and indexed with FAISS for the actual similarity search. A hybrid rerank blends BM25 lexical scoring into that dense-retrieved candidate pool afterward, not a naive full-corpus fusion of the two: that specific shape was chosen because it preserved cases naive fusion lost to lexical noise while eliminating cross-language contamination, measured against the alternative, not assumed.

investigate: true reframes results as unverified candidates with a falsification hint instead of ranked answers — a semantic match is correlation with a query, not proof a location causes whatever an agent is actually investigating. And this isn't only reachable over raw HTTP: a real A2A endpoint (agent card + message:send, not just a discovery manifest) sits alongside the MCP server and LangChain/CrewAI tools, so another agent can find and call this one without a human wiring up the integration first.

New — agentic commerce

Also routes AI-agent buyers to real sellers. Never touches a payment.

The Agentic Commerce Protocol (OpenAI + Stripe) defines checkout between one buyer-agent and one already-known merchant — its own spec has no seller_id field at all, and explicitly leaves multi-seller discovery to "the marketplace layer above this API." That layer doesn't really exist yet as a standard. This is a real, working implementation of it: a seller registers a real ACP checkout_session_url and a listing feed; a buyer-agent describes what it wants in plain language; matching reuses this same search engine. The match returned is the seller's own endpoint — the buyer's agent calls it directly to actually transact. This service never sees payment credentials, never proxies checkout, never holds funds.

Google didn't join ACP — it built a separate, non-interoperable standard (Universal Commerce Protocol, launched 2026-01-11 with Shopify/Etsy/Wayfair/Target/Walmart). Read directly from its real spec: it has the exact same gap ACP does, no cross-merchant discovery defined either. Same fix, second protocol — this catalog is also a real UCP business (/.well-known/ucp, /ucp/catalog/search), reusing the identical search underneath, not a second implementation. See the full walkthrough below.

Ranking also learns: a real Spikeling spiking-neuron network (not a counter) gives each buyer key its own memory of which listings keep getting returned or actually purchased, persisted across restarts. Two real bugs were caught by testing this against the live server rather than only a mocked suite — one where a strong "confirmed purchase" signal could self-erase via the same threshold-crossing mechanism that makes the neuron fire — both fixed and now covered by regression tests. Honestly disclosed, not hidden: purchase feedback is self-reported by the buyer's own agent, not independently verified against the seller's real transaction, since this service deliberately never sees it.

Everything above, working together

One real flow: search, sell, buy, confirm, trust — and it's reachable two ways.

Every call below is real and runs against the actual live API — not illustrative pseudo-output. Same account, same credit balance, start to finish.

1. Sign up once. Free trial credits, no payment needed to start.

$ curl -X POST https://api.observe-search.online/v1/signup \
-d '{"email":"you@example.com"}'
 
→ {"api_key":"obs_...", "checkout_url":"...", "note":"100 free trial credits"}

2. A seller lists a product — free. Their own real ACP checkout endpoint, nothing else.

$ observe commerce-register-seller "Trailhead Outfitters" "https://trailhead.example.com/checkout_sessions"
→ Registered seller_id=1
 
$ observe commerce-add-listings 1 '[{"item_id":"boots-1","name":"Waterproof Hiking Boots","description":"Rugged waterproof boots for muddy trails","unit_amount":12000}]'
→ Added 1 listing(s).

3. A buyer-agent describes what it wants. Real semantic ranking, plus a real match_id for what happens next.

$ observe commerce-search "waterproof boots for a muddy trail"
→ [Trailhead Outfitters (seller_id=1)] Waterproof Hiking Boots — 120.00 usd (score 0.94)
checkout: https://trailhead.example.com/checkout_sessions item_id=boots-1 match_id=1a75e62e-...

4. The buyer's agent completes the purchase directly with the seller (this API is never in that call — see above), then reports back what happened.

$ observe commerce-feedback 1 boots-1 purchased --match-id 1a75e62e-...
→ Recorded and reinforced -- this listing's learned affinity for your key just grew from real ground truth.

5. The seller independently confirms the same real event. This is what makes the trust network real instead of self-reported: two disconnected parties, one shared match_id, agreeing.

$ observe commerce-seller-feedback 1a75e62e-... fulfilled --rating 5
→ Recorded. Contributes to the buyer key's reputation tier.

6. The buyer's tier is now real, earned history — a buyer's own "purchased" claims alone can never reach verified; only independent seller confirmation gets there. One real dispute resets a key straight back to new.

$ observe commerce-reputation
→ Tier: trusted
Buyer-confirmed purchases: 1 Seller-confirmed fulfillments: 1 Disputes: 0
 
# and any seller can check an incoming buyer the same way, without seeing their identity:
$ observe commerce-verify-match 1a75e62e-...
→ Tier: trusted Seller-confirmed fulfillments: 1 Disputes: 0

7. The whole network's health is public — no key needed, nothing individually identifiable.

$ curl https://api.observe-search.online/v1/commerce/network-stats
→ {"total_agents":1,"verified_agents":0,"trusted_agents":1,"total_matches":1,"total_confirmed_transactions":1,"total_disputes":0}

8. The exact same catalog is also a real Google UCP business — a second, non-interoperable protocol, same listings, no separate integration.

$ curl https://api.observe-search.online/.well-known/ucp
→ {"ucp":{"version":"2026-04-08","services":{"dev.ucp.shopping":[{"transport":"rest","endpoint":".../ucp"}]},
"capabilities":{"dev.ucp.shopping.catalog.search":[...]},"payment_handlers":{}}}
 
$ curl -X POST https://api.observe-search.online/ucp/catalog/search \
-H "X-Api-Key: obs_..." -d '{"query":"waterproof boots for a muddy trail"}'
→ {"ucp":{"version":"2026-04-08","status":"success"},
"products":[{"id":"1:boots-1","title":"Waterproof Hiking Boots","price_range":{"min":{"amount":12000,"currency":"USD"},...}}]}

Same account, same listings, same learned trust — reachable as code search, ACP commerce, UCP commerce, CLI, MCP, A2A, LangChain, or CrewAI, because every one of those is a thin layer over the exact same underlying search/rank/reputation logic, not seven separate implementations that could drift from each other.

Pricing

Priced under what a search saves, not around what it costs to run.

$5 / 50,000 credits
≈ $0.0001 per search 1 credit deducted per call, refunded automatically on a failed search

A search's own marginal compute cost is close to zero — one embedding and a matrix multiply against a model that's already warm in memory. The real constraint isn't infrastructure, it's whether querying beats the token cost of not querying. At typical model API pricing, a few thousand tokens saved is worth a fraction of a cent — so the price per call is set to clearly undercut that, not to price the compute.

New keys start with a small free trial balance, so you can run real queries before buying credits. Indexing a repo of your own via /v1/private/index costs substantially more per repo than a single search — it's a real one-time compute cost (cloning and embedding an entire codebase), not a marginal query.
